# ТЗ: Fabric-мод «AFK Farm Telegram Notifier» для Minecraft 26.2

## Контекст и стек

Пиши **client-side** Fabric мод для **Minecraft Java Edition 26.2**. Мод следит за состоянием игрока на сервере (AFK-ферма) и шлёт уведомления в Telegram. **Все настройки (в т.ч. API-токен и chat_id) настраиваются прямо в игре** через экран конфига в Mod Menu.

Критично для 26.2:
- Версия **не обфусцирована**. Yarn больше не поддерживается — используй **официальные Mojang mappings** (`loom.officialMojangMappings()` в `build.gradle`). Никакого Yarn.
- **Java 25** минимум для Gradle JVM.
- **Loom 1.17**, **Gradle 9.5.1**, **Fabric Loader 0.19.3+**, **Fabric API 0.156.0+26.2** (или новее — проверь на Fabric Develop).
- Мод чисто клиентский: в `fabric.mod.json` окружение `"client"`.

Зависимости для настроек:
- **Cloth Config API** `26.2.155+fabric` (или новее) — реализация экрана настроек.
- **Mod Menu** `v20.0.0-beta.2+26.2` (или новее) — точка входа в экран настроек из списка модов. Реализуй `ModMenuApi` → `getModConfigScreenFactory()`.

## Сборка — ТОЛЬКО в Docker

На хост-машине **нет ни JDK, ни Gradle, ни каких-либо зависимостей**. Вся сборка идёт исключительно внутри Docker-контейнера. Агент не должен рассчитывать на локальные `java`/`gradle`.

Требования:
- Положи в корень проекта **`Dockerfile`** для сборки. Базовый образ с **JDK 25** (напр. `eclipse-temurin:25-jdk` или аналог; проверь, что тег существует, иначе возьми ближайший официальный образ с Java 25). Gradle не ставить в образ отдельно — использовать **Gradle Wrapper** (`./gradlew`), который тянет нужную версию (9.5.1) сам.
- Dockerfile должен: скопировать исходники, прогнать `./gradlew build --no-daemon`, и оставить готовый `.jar` доступным (напр. в `/out` или через volume-mount на `build/libs`).
- Положи **`.dockerignore`** (исключить `.gradle/`, `build/`, `run/`, `.git/` и т.п.).
- Добавь **скрипт-обёртку `build.sh`** (`set -euo pipefail`, комментарии на русском), который:
  1. собирает образ (`docker build -t afk-notifier-build .`),
  2. запускает контейнер со сборкой и **выкладывает готовый jar на хост** через bind-mount (напр. `-v "$PWD/build/libs:/app/build/libs"`), чтобы `.jar` оказался в `build/libs/` на хосте без установки чего-либо локально.
- Внутри контейнера учти доступ в сеть для Gradle (скачивание Loom, Fabric, Cloth Config, Mod Menu, MC-артефактов). Разрешённые для скачивания источники: Maven Central, `maven.fabricmc.net`, `maven.shedaniel.me` (Cloth Config), `maven.terraformersmc.com` (Mod Menu), `libraries.minecraft.net`. Не завязывайся на кэш хоста; при желании можно смонтировать `~/.gradle` как кэш-volume для ускорения повторных сборок, но сборка должна работать и без него.
- В инструкции опиши: как собрать (`./build.sh` или две команды docker), где появится jar на хосте, как повторить сборку начисто. Никаких шагов, требующих Java/Gradle на хосте.
- **Важно:** только сборка идёт в Docker. Сам мод в контейнере не запускается — это клиентский мод, его кладут в `mods/` реального клиента.

## Функциональные требования

Мод отслеживает 5 событий и по каждому шлёт сообщение в Telegram. Формат даты/времени: локальное время системы, `dd.MM.yyyy HH:mm:ss`.

1. **Получение урона игроком.** При каждом уменьшении HP клиентского игрока отправить: дата/время, размер полученного урона (сколько HP снято), текущее HP после урона (`X / MaxHP`). Источник урона указать, если доступен.
2. **Смерть игрока.** Отправить: дата/время, текст «Бот для фарма умер». Если доступна причина смерти (death message) — добавить.
3. **Дисконнект с сервера.** Отправить: дата/время, причина дисконнекта (текст disconnect/kick reason, если есть).
4. **Успешный коннект на сервер.** Отправить: дата/время, адрес сервера.
5. При старте мода писать в лог, что он загрузился.

## Технические детали реализации

- **HP-мониторинг:** `ClientTickEvents.END_CLIENT_TICK`, храни предыдущее значение `player.getHealth()`, сравнивай с текущим. Если текущее < предыдущего — это урон, посчитай дельту. Сбрасывай при респавне и при null-игроке. Мод клиентский, поэтому детект через изменение здоровья за тик, а не через серверные damage-события.
- **Урон/источник:** если через тик источник недоступен, ограничься дельтой HP. Death message бери из клиентского combat tracker / disconnect-экрана, если доступен.
- **Коннект/дисконнект:** `ServerPlayConnectionEvents.JOIN` и `DISCONNECT` из Fabric API. Причину дисконнекта тяни из аргументов события.
- **Не спамить:** урон одним пакетом за тик = одно сообщение. Добавь троттлинг (не чаще 1 сообщения об уроне в `damageThrottleMs`), чтобы DoT-эффекты (яд/огонь) не заспамили Telegram.

## Telegram-интеграция

- Отправка через Bot API: HTTP POST на `https://api.telegram.org/bot<TOKEN>/sendMessage` с параметрами `chat_id` и `text`.
- Используй `java.net.http.HttpClient` (встроен в JDK, без внешних зависимостей).
- **Все сетевые вызовы — асинхронно** (`sendAsync` или отдельный executor). Никаких блокирующих запросов в игровом потоке — фризит клиент.
- Метод отправки должен возвращать результат (успех/ошибка + HTTP-код + тело ответа Telegram) — это нужно кнопке Test (см. ниже).
- Ошибки отправки логируй, но не роняй мод и не спамь в чат.

## Конфигурация — целиком в игре

Настройки хранятся в `run/config/afk-notifier.json` (запись/чтение через Cloth Config или свой сериализатор на Gson), но **редактируются через экран Mod Menu**, не руками в файле.

Экран настроек (Cloth Config `ConfigBuilder`), категории и поля:

**Основное:**
- `enabled` (boolean) — глобальный вкл/выкл.
- `botToken` (String, текстовое поле) — **токен Telegram-бота**. Вводится в игре. Поле желательно пометить как чувствительное; если Cloth поддерживает скрытый/пароль-филд — используй, иначе обычный `stringField` с подписью-предупреждением «не показывать стрим/скриншот».
- `chatId` (String) — **id чата/пользователя**, кому слать. Строкой (chat_id может быть отрицательным для групп).
- **Кнопка «Test» (Отправить тестовое сообщение)** — см. отдельный раздел.

**События (отдельная категория):**
- `notifyOnDamage` (boolean)
- `notifyOnDeath` (boolean)
- `notifyOnDisconnect` (boolean)
- `notifyOnConnect` (boolean)
- `damageThrottleMs` (int, дефолт ~3000) — троттлинг сообщений об уроне.

**Требования к экрану:**
- Значения применяются и сохраняются в файл по кнопке Save в экране Cloth Config (`setSavingRunnable`).
- Локализация подписей полей через `lang/ru_ru.json` и `en_us.json`.
- Если `botToken` или `chatId` пустые — мод работает, но отправку не делает, пишет предупреждение в лог.
- **Токен не хардкодить** и не коммитить.

## Кнопка «Test» в настройках

Кнопка на экране конфига, которая проверяет связку токен+chat_id **прямо из игры**, без ожидания реального события.

Поведение:
1. Реализуй как элемент Cloth Config, вызывающий действие по клику. Cloth не имеет «чистой» кнопки-действия в API — реализуй через собственный `AbstractConfigListEntry` с виджетом-кнопкой (или иной надёжный способ под текущую версию Cloth) и опиши выбранный подход в комментарии.
2. При клике брать **текущие введённые в поля значения** `botToken`/`chatId` (не обязательно уже сохранённые в файл), чтобы можно было протестировать перед сохранением.
3. Отправлять тестовое сообщение: `✅ AFK Notifier: тестовое сообщение. Связь с Telegram работает.\n🕐 {дата/время}`
4. Вызов асинхронный, кнопку на время запроса дизейблить (защита от даблкликов).
5. Показать результат игроку:
   - **Успех** (HTTP 200, `ok: true`) — тост/сообщение «Тест пройден, сообщение отправлено».
   - **Ошибка** — показать код и описание из ответа Telegram (напр. `401` → «неверный токен», `400 chat not found` → «неверный chat_id»). Разобрать поле `description` из JSON-ответа Telegram и вывести его.
   - Результат выводить и в лог, и в UI (`SystemToast` или сообщение).
6. Если поля пустые — не слать запрос, сразу показать «Заполните токен и chat_id».

## Шаблоны сообщений (с эмодзи)

Дефолтные тексты (можно вынести в константы):
- Урон: `🩸 Получен урон\n🕐 {дата/время}\n💥 Урон: {delta} HP\n❤️ Текущее HP: {current}/{max}{источник, если есть: \n☠️ Источник: {src}}`
- Смерть: `💀 Бот для фарма умер\n🕐 {дата/время}{death message, если есть: \n📜 {msg}}`
- Дисконнект: `🔌 Отключение от сервера\n🕐 {дата/время}\n📋 Причина: {reason}`
- Коннект: `✅ Подключение к серверу\n🕐 {дата/время}\n🌐 Сервер: {address}`
- Тест: `✅ AFK Notifier: тестовое сообщение. Связь с Telegram работает.\n🕐 {дата/время}`

## Структура проекта

Стандартный Fabric mod template + Docker:
- `Dockerfile`, `.dockerignore`, `build.sh` (сборка в контейнере)
- `build.gradle`, `gradle.properties`, `settings.gradle`, `gradle/wrapper/*`
- `src/main/resources/fabric.mod.json` — entrypoints: `client` (основной) и `modmenu` (`ModMenuApi`); зависимости: `fabricloader`, `minecraft`, `fabric-api`, `cloth-config`, `java >=25`.
- `src/client/java/<пакет>/`:
  - основной класс (`ClientModInitializer`)
  - `TelegramClient` (метод отправки возвращает результат для Test)
  - `ModConfig` (модель + загрузка/сохранение)
  - `ModConfigScreen` / фабрика экрана Cloth Config (включая кнопку Test)
  - `ModMenuIntegration implements ModMenuApi`
  - класс с обработчиками событий
- `src/main/resources/lang/ru_ru.json`, `en_us.json`
- Миксины скорее всего не нужны — сначала пробуй callback-события Fabric API.

## Порядок работы

1. Сначала подготовь `Dockerfile` + `build.sh` и убедись, что **сборка пустого шаблона под 26.2 проходит внутри контейнера** и jar появляется на хосте. Только Docker, без локальных инструментов.
2. Собери базовый шаблон под 26.2 (Fabric Example Mod, ветка 26.2), проверь `./gradlew build` в контейнере.
3. Подключи Cloth Config + Mod Menu, сделай пустой экран настроек, открой из Mod Menu — проверь.
4. Реализуй `ModConfig` (загрузка/сохранение) → поля экрана → `TelegramClient` с возвратом результата.
5. Добавь кнопку Test, проверь на реальном боте оба сценария (успех и неверный токен).
6. Обработчики событий: сначала connect/disconnect, потом HP-монитор и death.
7. Финальная сборка в контейнере, готовый `.jar` в `build/libs/` на хосте.
